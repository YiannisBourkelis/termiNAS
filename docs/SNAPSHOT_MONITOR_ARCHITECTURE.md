# Snapshot Monitor Architecture

This document describes how termiNAS detects uploads and turns them into immutable
Btrfs snapshots. The implementation is `/var/terminas/scripts/terminas-monitor.sh`,
generated by `src/server/setup.sh` and run by `terminas-monitor.service`.

## Design in one paragraph

Every Btrfs subvolume carries a **generation** counter that the kernel increments
whenever anything inside the subvolume changes. The monitor polls
`btrfs subvolume list -c /home` (one cheap call that lists every subvolume with its
current generation and its creation generation), and for each user compares the
`uploads` subvolume's generation with the creation generation of the user's newest
snapshot. If uploads is newer, `btrfs subvolume find-new` confirms that real data was
written, and a snapshot is taken once the generation has been stable for the inactivity
window. Cost is independent of the number of files or directories a user has.

## Detection

```
uploads.gen > newest_snapshot.cgen        something changed since the last snapshot
  and find-new(uploads, cgen) non-empty   ... and it was data, not just metadata
```

- **Generation comparison** is a single field comparison per user, from one ioctl per
  poll. New users appear automatically (their subvolume shows up in the listing) and
  deleted users disappear.
- **`btrfs subvolume find-new <uploads> <cgen>`** lists data extents written after a
  generation using the tree's own generation bounds, so it is fast even on very large
  trees. It filters out changes that move the generation without writing data:
  atime updates from a client listing the share (`/home` is mounted `noatime` by
  `setup.sh` to avoid most of these), permission changes, and pure deletions. Without
  this gate, every directory listing by an idle client would produce an empty snapshot.
- Snapshot creation COWs the source root, so right after a snapshot the uploads
  generation equals the snapshot's creation generation and the user reads as idle.
  A restart never loses pending work: the comparison is against on-disk state, not
  in-memory events.

## Timing

| setting | default | meaning |
|---|---|---|
| `TERMINAS_POLL_INTERVAL` | 10 s | how often generations are read |
| `TERMINAS_INACTIVITY_WINDOW` | 60 s | quiet time (no generation change) before a snapshot |
| `TERMINAS_SNAPSHOT_INTERVAL` | 1800 s | maximum continuous activity before a snapshot is forced |
| `TERMINAS_DEBUG` | 0 | `1` logs every generation change |

Set these as `Environment=` lines in the `[Service]` section of
`/etc/systemd/system/terminas-monitor.service` (preserved across `setup.sh` runs).

Detection latency is the Btrfs commit interval (30 s by default, `commit=` mount
option) plus the poll interval: generations only move when a transaction commits. A
snapshot therefore follows the last write by roughly 70–100 s. The forced snapshot after
`TERMINAS_SNAPSHOT_INTERVAL` covers very long uploads; files still open for writing are
excluded from it and captured by the final snapshot when the upload completes.

## Snapshot creation

1. Skip if `uploads/` is empty.
2. `btrfs subvolume snapshot uploads versions/<YYYY-MM-DD_HH-MM-SS>` (writable).
3. Remove from the snapshot any file some process holds open for writing. Open files
   are found by scanning `/proc/*/fd` symlinks that point under the user's uploads and
   checking the open flags in `/proc/*/fdinfo`, so the cost is proportional to open
   descriptors on the host, not to the user's file count (`lsof +D` walked the tree).
4. `chown root:backupusers`, `chmod 755` on the snapshot directory (files inside keep
   their original ownership), then `btrfs property set -ts <snap> ro true`.
5. Log `Btrfs snapshot created for <user> at <timestamp> (<reason>)`.
6. Run the hybrid quota check (below).

Snapshots are read-only Btrfs subvolumes owned by root; chrooted SFTP users can read
their own `versions/` but cannot modify or delete anything in it.

## Quota hook

After each snapshot the monitor sums the *exclusive* bytes of the user's uploads and all
snapshots from one `btrfs qgroup show --raw` call (parsed by `build_qgroup_usage_cache`
in `common.sh`) and compares the total with `.terminas-quota-limit`. Over the limit it
sets the uploads qgroup limit to 1 byte (blocks writes) and writes
`.terminas-quota-exceeded`; under the limit it restores the configured limit and removes
the flag. A blocked user's generation changing (deletions) triggers a re-check on the
next poll. The nightly cleanup re-checks blocked users as well.

This relies on **simple quotas** (`btrfs quota enable --simple`); see
`QUOTA_ARCHITECTURE.md` for why full qgroup accounting is not used and what simple
quotas cannot report.

## Health signals

- `/var/run/terminas/heartbeat` is touched every poll. `manage_users.sh status`
  reports CRITICAL if it is older than a few poll intervals while the service is
  active (a hung loop that systemd still considers running).
- `/var/run/terminas/pending_<user>` holds the epoch since which a user has uncaptured
  changes. `status` reports CRITICAL when one is older than the maximum snapshot
  interval. Markers are removed after the snapshot or when the user is deleted.
- The unit uses `Restart=always`: any exit, clean or not, is restarted after 5 s.
- Log: `/var/log/terminas.log` (rotated weekly).

## Cost profile

| operation | cost | frequency |
|---|---|---|
| `btrfs subvolume list -c /home` | ~70 ms for hundreds of subvolumes | every poll |
| `btrfs subvolume find-new` | milliseconds (generation-bounded tree walk) | once per changed generation per user |
| `/proc/*/fd` scan | milliseconds | once per snapshot |
| `btrfs qgroup show` | ~0.3 s | once per snapshot (with a quota limit set) |
| `btrfs subvolume snapshot` | milliseconds | once per snapshot |

Memory is a single bash process with a few associative arrays. Nothing scales with
the number of files or directories.

## History

Until September 2026 the monitor used `inotifywait -m -r /home`, which places one
kernel watch on every directory. A user with roughly 500,000 directories exhausted
`fs.inotify.max_user_watches` (524,288) after a 13-minute startup that peaked at
650 MB of RAM; inotifywait exited, the shell pipeline reported a clean exit, and
`Restart=on-failure` never restarted the service, which stayed dead for six days.

The inotify design had further costs: the main loop spawned several processes per
event and fell behind on large uploads (events dropped when the kernel queue
overflowed), `lsof +D` walked the whole tree twice per snapshot, the periodic-snapshot
check compared the wrong timestamp and could never fire, and the watches held
references to deleted inodes so Btrfs could not reclaim space after snapshot or user
deletion until the service restarted ("pending deletions"). A per-user-watcher design
and a signal-triggered restart were proposed to address the last point but never
implemented; generation polling removed all of these issues at once. Do not
reintroduce recursive inotify.
